# 设计逻辑可视化（Git 图式）

把梳理好的**设计逻辑**画成一张可读的时序图：同一入口串联推进，不同入口并行分岔，必要时再分支；用户能一眼抓住主线，也能点开细节与数据表。

## 自顶向下：四个部分

### 第一部分：数据 / 内容来源

**全部要依据文档来去拆分出这个可视化的方案。**

1. 唯一真相源：用户已确认的逻辑设计文档（通常 `docs/Engineering/backend/{模块}.md`；前端同理用 frontend 文档）。
2. 禁止凭代码臆造「文档没有写的流程」；文档未写清处标「待确认」，不要假装已定。
3. 拆分可视化方案时：先读文档的入口、数据流、数据表与生命周期，再映射为路径与卡片；**不是**先画图再回头凑文档。
4. 正文尽量少删减。文档里英文名后的中文括号注释（如 `RealnameUser`（概念：…））必须保留。
5. 术语跟文档：表单用「表单」，不要用未定义的 Schema 充当业务词（字段名 `form_schema_json` 可保留并附中文说明）。

### 第二部分：卡片种类与写法

我们有三种卡片。

#### 1）入口卡片（Trigger / Entry）

- **什么叫入口 / 触发**：用户在用户端，或管理员在后台的一个操作，叫做触发；这叫做入口。**其他的都不叫做入口或者触发。**
- 系统回调（如 `on_paid` / `on_closed`）、内部函数调用、汇入中段的节点——挂在所属路径下，**不**升格为顶层入口。
- **颜色**：特殊颜色——红色 / 深红色 / 很艳丽的红色，代表流程开始。推荐：边框 `#c41e3a`，路径起点可再加重（更粗边框 + 浅红底）。
- 卡片上可标小字：`入口 · 流程起点` 或 `入口 · 用户/管理员触发`。
- 每个文档入口 = 一条 Git 路径的起点（`pathStart`）；同一条路径内后续步骤串联。

#### 2）正常逻辑卡片（Step / Decision）

内容**不能太多也不能太少**：

- **太多**：注意力都放在这一个卡片上了 → 应拆分。
- **太少**：注意力太分散、卡片链过长 → 应合并相关健全/校验。

**粒度标准（执行用）**

| 规则 | 说明 |
|------|------|
| 默认折叠 | 标题一行可读懂「这一步干什么」；细节点开再看 |
| 相关合并 | 同一意图下的健全（如实名 + 上架 + 活跃去重）可同卡分点 |
| 无关分卡 | 鉴权意图 vs 建单动作 vs 支付回调 vs 履约，勿糊成一张 |
| 展开体量 | 展开后建议 **3～7 条** bullet；超过 8 条优先拆卡或升决策分支 |
| 折叠高度 | 折叠卡视觉高度尽量接近（约一行标题 + 可选状态标签），避免某张远高于邻卡 |
| 决策卡 | `◆` 虚线框；每个分支都要画出（含「否」）；禁止把分支只写在正文里 |

决策后的「是 / 否」各自成链；共享中段用 **汇入**（见交互），不要复制一整条子树。

#### 3）数据表卡片（Table Hub）

- 绿色虚线框；默认停在画布右侧表栏；点击关联逻辑卡时吸附过来。
- **字段要横着写**：横着的一个表格——**上面是字段的名称，下面是对应的中文名**。
- **生命周期**：展开为**分支卡片**形式（每条路线一张小卡，状态有序编号 + 括号因果），默认折叠。
- 逻辑卡上用「读 / 写 / 读写」chip 标明对本表的操作。

### 第三部分：布局结构（设计逻辑）

目标形态接近 **Git 提交图**，不是扁平思维导图：

```
路径 A（入口深红）──●──●──◆──●──●
                         ╲
                          ●──●
路径 B（另一入口）──●──●──→（点击汇入路径 A 某节点）
路径 C …
右侧：数据表栏（未聚焦时）
```

1. **同一入口**：严格时序串联（左→右）。
2. **不同入口**：上下并行分路径，互不假装成同一条线的兄弟节点。
3. **真分支才分叉**：文档里的条件判断 → 决策菱形 + 多 branch；不是分类标题并列。
4. **数据表不是下一步**：关联表卡只挂在逻辑卡的**上面或下面**，绝不挂在流程前/后（左右）。否则会被读成「下一步是数据库」。
5. **汇入时序**：分支终点若进入已有时序，用「→ 时序：{目标标题}」芯片指向真实节点；**主时序线保持干净**；点击芯片再显示到目标的连线（虚线弧），并可滚动高亮目标。

视觉：Kami 羊皮纸底 `#f5f4ed`，主时序线墨蓝；入口红；表卡翠绿；状态枚举用彩色 code chip。

### 第四部分：交互与静态全景

#### 交互（默认交付）

必须支持：

1. **碰撞检测**：卡片之间不要互相遮挡；展开/吸附后把挡路的逻辑卡推开（表卡作障碍物时优先下推或上推，不把表塞进时序左右）。
2. **连线文字不被遮挡**：分支 label 落在弯道空隙；密度高时宁可加大间距，不要让卡压住 label。
3. **卡与线也不要无意义遮挡**：聚焦吸附时用竖向连线连表卡上下边；跨路径汇入线仅在点击时出现，避免常驻乱线。
4. 逻辑卡 / 表字段 / 生命周期均可展开折叠；缩放、搜索、展开全部 / 折叠全部。

#### 静态全景图（不要动态交互时）

最终目的仍是让用户理解整个意图。若只要一张静态图：

1. **先按同一套语义排版**（Git 路径 + 三类卡），不要另起一套「海报式」信息架构。
2. **默认全展开决策分支**；逻辑卡可只显示标题 + 关键状态 tag（细节进脚注区或侧栏小字），避免一张 PNG 上万字。
3. **表卡**：选「本模块主表」固定在对应主干下方（仍上下关系），字段用紧凑横表；生命周期每路线一行编号，勿展开成长文。
4. **汇入**：静态模式下允许画**淡虚线**汇入边（比交互更淡），或在汇入点旁写 `→ 见路径A「用户提交留资」`，二者选一，避免又连线又大段说明。
5. **入口**仍用深红，保证静态图上「从哪开始」一眼可辨。
6. 导出：浏览器全景截图 / 打印 PDF；或 `expandAll` 后截图。尺寸与留白见 [reference.md](reference.md)。

## 执行工作流

```
已确认逻辑设计 md
  → 对照 examples.md 案例图（全景 / 展开 / 横表 / 汇入）
  → 用 templates/ 建或改 artifact（结构 + CSS + 数据骨架）
  → 列出入口（仅用户/Admin 触发）与数据流
  → 拆 Git 路径（共享前缀合并，中段汇入不复制）
  → 写三类卡片数据（保真文档注释）
  → 布局 + 碰撞 + 上下吸附表卡
  → bundle 单 HTML → preview
  →（可选）全展开导出静态全景；必要时更新 assets/examples 截图
```

1. 读 md：入口、数据流编号、表与生命周期、待确认项。
2. 打开 [examples.md](examples.md)，确认目标视觉与交互对齐案例。
3. 按 [templates/project-structure.md](templates/project-structure.md) 搭目录；数据从 [data-skeleton.ts](templates/data-skeleton.ts) 填起；样式对齐 [styles.css](templates/styles.css)。
4. 建 `paths[]`：每入口一条；共享段抽成链，用 `jumps` 汇入。
5. `bash ~/.cursor/skills/web-artifacts-builder/scripts/bundle-artifact.sh`，复制到 `docs/un-commit/preview/`。
6. 自查清单通过后再交给用户阅览。

## 交付前自查

### 来源与语义

- [ ] 每条路径能指回文档入口 / 数据流编号
- [ ] 无「系统回调」顶层入口
- [ ] 中文括号注释未删；无擅自 Schema 化业务词
- [ ] 决策「是/否」都在图上

### 卡片

- [ ] 入口深红可辨
- [ ] 逻辑卡粒度：无巨型单卡、无碎步刷屏（展开约 3～7 点）
- [ ] 表字段为横表（英文字段名上行 / 中文下行）
- [ ] 生命周期为可展开分支卡

### 布局与交互

- [ ] 同入口串联；异入口并行
- [ ] 表卡只上下吸附，不在流程左右
- [ ] 无卡片互叠；展开后仍不压线标
- [ ] 汇入点击可出连线并跳到真实时序节点

### 静态（若需要）

- [ ] 全景仍是 Git 时序，不是重新做的信息海报
- [ ] 入口色与汇入关系在无点击时仍可读

## 反模式（禁止）

- 思维导图式「分类并列」冒充流程
- 把数据库画在步骤左右，读成下一步
- 把 `on_paid` 等做成与用户操作平级的入口
- 为减少线而删掉「否」分支
- 关键词电报体步骤（须保留因果，与文档一致）
- 常驻满屏汇入线导致主时序不可读
